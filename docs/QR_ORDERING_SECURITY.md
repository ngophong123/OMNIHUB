# QR ordering security

Public routes are limited to `GET /public/qr/:token/menu`, `POST /public/qr/:token/session`, `GET /public/table-sessions/me`, `POST /public/table-sessions/orders` and `GET /public/order-status/:trackingToken`. Public credentials are 32 bytes from the operating-system random source, encoded as 64 hexadecimal characters. QR credentials, customer-session credentials and order-tracking credentials are separate capabilities; PostgreSQL stores SHA-256 hashes, never their raw values. QR rotation invalidates table sessions created by the previous credential generation.

The table and store are resolved only from the QR hash. A customer session is resolved only from its hash and server-side tenant/store/table relationships. Order creation rechecks the session, expiry, active table, current QR generation and store-level QR flag inside the serializable command transaction. Product IDs and selections are reloaded in the authenticated store; prices and recipe requirements are recomputed, and ingredient reservations use the same conditional PostgreSQL updates as POS. A submitted total is rejected by the strict order schema.

Order tracking uses a different hash, reveals one order's safe status projection and joins only a server-selected per-order socket room. The customer cannot choose a store or room. Socket events contain only a refresh notification; the browser obtains status through the scoped REST endpoint. Socket origin validation remains exact. Public QR and tracking routes are rate limited to 60 requests per minute per source IP by the API process; login has its own limit. The current limiter uses process memory, so production multi-instance deployments must use a shared rate-limit store and configure trusted proxy handling to prevent spoofed client IPs.

All state-changing routes continue to require the configured `WEB_ORIGIN`. The customer UI must be hosted at the exact origin configured as `WEB_ORIGIN`; do not accept arbitrary origins. API logs redact QR and tracking path tokens. HTTPS image URLs are accepted for public product images. Production must configure `QR_TOKEN_SECRET` as a stable, randomly generated secret of at least 32 characters. The development-only fallback is disabled in production; order acceptance fails closed if the production secret is missing.

The QR code itself is a bearer capability intended to be printed in a public dining area. Anyone who scans it can browse and submit an order for that table while ordering is enabled. A manager can disable ordering or rotate a compromised code. This milestone does not implement customer identity, payment, remote order cancellation, bot challenge, distributed rate limiting, abuse analytics or production penetration testing.
