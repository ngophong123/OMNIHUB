## Disaster recovery design and measured evidence — 2026-10-24

**Pilot NO-GO.** The 15-minute objective is a maximum tolerable data-loss window at a declared incident. A five-minute dump interval is only the *creation cadence*. The age of the latest independently recoverable point is the operational proxy for that window, not proof of actual lost transactions. Actual loss needs the time and identity of the last committed transaction before failure plus a comparison with the restored state. The observed **35,797-second** age at host restart is a policy failure; the actual data-loss window is **unknown** because no transaction timeline or declared failure instant was captured. The exact host-down duration is likewise unmeasured: the last verified point was 2026-10-23 12:57:33 UTC, but a recovery point is not a host-shutdown timestamp. The local monitor first emitted `BACKUP_STALE` at 22:54:10 UTC. Its 900-second threshold had elapsed at approximately 13:12:33 UTC, so notification was unavailable for at least **34,897 seconds** after the threshold; this is detection at restart, not delivered paging. The first post-restart dump failed while PostgreSQL started. Valid 300-second scheduled points after recovery prove the scheduler resumed, not outage tolerance.

**Chosen pilot architecture:** keep the verified five-minute PostgreSQL custom-format dump and local encrypted Restic repository; copy each verified snapshot to an operator-approved, independently powered and administered HTTPS Restic repository on another host/storage fault domain. Use separate source and destination credentials and a dedicated read-only monitoring credential on a third independent execution environment. That monitor checks primary health, remote snapshot age, Restic repository integrity, and daily full decrypt/restore/checksum/archive verification every 60 seconds, and sends critical events to an operator-approved HTTPS webhook. The target is RPO ≤900 s and site RTO ≤3600 s, measured from incident declaration through usable service including detection, operator action, key retrieval, data recovery and cutover. A remote recovery point must be *verified*, not merely uploaded; if it ages past 900 s, the service is outside its RPO and must alert. No automated claim of continuous RPO is possible while offsite copy and independent monitoring are not running.

For this small pilot, a full dump every 300 s is the simplest recoverable unit and the measured local restore is fast. Budget for a separately powered host or approved storage account, transfer/egress, monitoring host, retention capacity, key custody, and operator time; exact monetary cost requires the chosen provider and database growth. Restic encrypts contents, but repository URL, timing and snapshot metadata remain operationally sensitive. TLS, least-privilege credentials, separately stored keys, approved alert recipient, immutable/offsite retention policy and regular restore checks are required. A single provider/account or site-wide power failure can still defeat the design; fault domains and operator access must be reviewed on the actual deployment.

PostgreSQL WAL archiving and point-in-time recovery are a later option if five-minute full dumps become too large or transaction loss must approach zero. A logical `pg_dump` **cannot** act as a WAL base backup; WAL/PITR requires a physical base backup plus an unbroken archived WAL sequence, independent transport, replay tooling and monitoring. `archive_timeout` reduces unarchived time at the cost of additional full WAL segments. Streaming replication can lower lag but adds a continuously managed standby and is not a substitute for tested backups. See the [PostgreSQL continuous-archiving guide](https://www.postgresql.org/docs/current/continuous-archiving.html), [WAL configuration](https://www.postgresql.org/docs/current/runtime-config-wal.html), and [standby/log-shipping guide](https://www.postgresql.org/docs/current/warm-standby.html). **WAL/PITR is not implemented; WAL archive-failure monitoring is not applicable to the selected architecture.**

## Create and verify a backup

```powershell
$env:DATABASE_URL = '<secret-manager supplied connection string>'
./scripts/backup-postgres.ps1 -RetentionDays 30
```

The script writes a custom-format `.dump` and SHA-256 sidecar under `.local/backups` by default, verifies that `pg_restore --list` can read the dump, then prunes only `omnihub-*.dump` backup files older than the configured retention inside that directory. Set `-RetentionDays 0` to disable pruning. Store copies in encrypted off-host storage with access restrictions; this local script does not provide encryption or offsite replication.

## Restore into a new isolated database

```powershell
./scripts/verify-postgres-restore.ps1 -BackupFile '.local/backups/omnihub-<timestamp>.dump'
```

The verifier checks the sidecar hash, confirms a newly generated `omnihub_restore_verify_<UTC timestamp>` database does not already exist, creates that separate database, restores the dump, and runs `prisma migrate status` against it. It never targets the database named in the source URL and refuses an existing target. It deliberately does not drop the restore database, even after a failure: inspect and remove it only after a separate, explicit review. The script reports restore duration but does not claim an RTO/RPO target.

## Recovery sequence

1. Declare the incident and stop application writers only if the incident commander directs it.
2. Identify the latest integrity-verified backup and the intended isolated or recovery target. Never restore over the existing development or production database as a test.
3. Restore to a new database, verify migration status and application-level critical queries, then record backup age, restore duration, migration result and operator.
4. For an actual recovery, have an authorized database operator select a recovery target, validate the recovered data and coordinate connection cutover. That cutover is deliberately outside these scripts.
5. Preserve the source and failed restore artifacts until evidence and retention requirements permit an explicitly approved cleanup.
